# transcribe.cpp patches

`speech` does not link a published transcribe.cpp release. It builds one from
source: `tools/vendor-transcribe.sh` clones the pinned tag, applies every patch
in this directory, and builds `vendor/TranscribeCpp.xcframework`, which
`Package.swift` points at. The patches live here, in this repository, so the
same clone plus the same patches produce the same library on any machine.

Pinned tag and commit: `PIN` in this directory. `./build.sh` moves it to the
newest release by default (`tools/vendor-transcribe.sh --update`), but only once
the framework builds from that release with every patch here applied; until
then it stays where it was, and `./build.sh --no-update` builds it.

## Layout

Patches directly in this directory apply at the root of the transcribe.cpp
clone. Patches in a `ggml/` folder here would apply inside its vendored `ggml/`
tree, because they are written against the ggml repository and are meant to go
to ggml unchanged - transcribe.cpp keeps its own downstream ggml patches in
`patches/ggml/` the same way. There are none at `v0.4.0`; the folder is created
when one is needed, and `tools/vendor-transcribe.sh` applies whatever is in it.

The vendored `ggml/` directory is generated by upstream's `scripts/sync-ggml.sh`
from an upstream ggml SHA (`ggml/UPSTREAM`; `d7cb574130e6` at `v0.4.0`) plus
that patch list. A ggml patch here patches the generated files directly instead
of re-running the sync script: the result is identical, and it keeps the build
off the network and off a second repository.

## The patches

### 0001-stream-commit-collapsed-spaces.patch

`src/transcribe-asr.cpp` (at `v0.2.3` the same function was in
`src/transcribe.cpp`), plus a regression test in `tests/stream_dispatch_unit.cpp`.

Still needed at `v0.4.0`: `token_prefix_raw_bytes` moved to
`src/transcribe-asr.cpp` unchanged, and the patch was carried over by changing
only its file name. Checked on 2026-10-15 with upstream's own unit test built
for the CPU: `transcribe_stream_dispatch_unit` fails four checks in the new
`collapsed_space_run` case on unpatched `v0.4.0` (the committed text stops
growing) and passes with the patch.

For the Parakeet cache-aware family the library's committed text stops growing 5
to 25 seconds into continuous speech (18 of 20 measured passages) and everything
after that is committed only at finalize. The commit boundary compares per-token
texts, each decoded on its own, against a full text whose runs of spaces have
been collapsed, so the first token that decodes to a bare space ends the match
for the rest of the stream. Partials stay current; finals, which refinement and
saved transcripts are built from, do not.

Measured on `ggml.nemotron-3.5-asr-streaming-0.6b` q8_0 over 20 continuous
LibriSpeech passages: finals 34.39 s behind the audio at the median and 54.27 s
at worst, on both an M5 and an M1 Pro. With this patch and no other change:
0.46 s median, 1.74 s worst, WER unchanged at 3.60%.

`SpeechGGML` also carries a Swift-side workaround for this defect
(`GGMLLiveSession.commitsTentative(for:)`, documented in `docs/live.md`). It is
inert against a patched library - it reads committed plus tentative as
committed, which is what the fixed library commits anyway - and stays until the
pin moves to a release that carries the fix.

Facts for the upstream issue and PR: `Private/transcribe-cpp-commit-freeze-facts.md`.

### Dropped at v0.4.0: the Metal out-of-memory crash

Until `v0.2.3`, two ggml patches here, `ggml/0002-metal-null-check-buffer-alloc`
and `ggml/0003-sched-check-reserve-result`, turned a failed Metal allocation from
a SIGSEGV into `run: out of memory` (a 20-minute recording through Qwen3-ASR
1.7B Q8_0, which asks Metal for 14.8 GB on a 24 GB machine). `v0.4.0` vendors
ggml `d7cb574130e6`, which carries both fixes - the null check as upstream
commit `e9c3b152bf`, and the checked `ggml_gallocr_reserve_n` in
`ggml_backend_sched_alloc_splits` - so both patches applied in reverse there
and were deleted. Facts: `Private/transcribe-cpp-metal-oom-facts.md`. The crash
itself should be re-checked on the first measuring run with this release.

## When a patch stops applying

The build fails, on purpose, and nothing is produced. A patch that no longer
applies means upstream changed the code a fix depends on, and the right response
is to look at what changed - not to ship a binary quietly missing the fix.

Before applying anything the script checks every patch on its own against the
clean tree and lists each one: `applies`, `DOES NOT APPLY` (rework it), or
`ALREADY IN <tag>` (the release carries the fix: delete the patch and its
section above). On an update to a newer release, `PIN` keeps the old release
until all of that is sorted out, so `./build.sh --no-update` keeps working.

To rework one:

1. Clone the tag the failed run named (the pin, or the newer release on an
   update) by hand, or use the one that run left in `vendor/transcribe.cpp`.
   Read `vendor/transcribe.cpp/.speech-patch-state` first: a tree left by a
   failure carries no patches (the pre-check failed) or only those ordered
   *before* the failing one, so it is a diagnostic tree, not the patched
   source. Never build from it - it compiles perfectly well and produces a
   library missing fixes. Only a tree whose state file says `complete` is what
   the shipped framework was built from.
2. Apply what still applies, fix the rest against the new code, and re-measure
   what the patch claims above. The numbers in this file are the acceptance
   criteria.
3. Regenerate the patch with `git diff` from the clone root (`git diff` inside
   `ggml/` for the ggml series) and drop it back here under the same name.
4. Run `tools/vendor-transcribe.sh --force`, adding `--update` when the patch
   was reworked for a newer release than `PIN` names (or run `./build.sh`).

If a fix has landed upstream, delete the patch instead.

## When upstream publishes a release

Every build checks for a newer tag; it costs one `git ls-remote`, and is skipped
with `SPEECH_VENDOR_OFFLINE=1`. A default `./build.sh` then builds the new
release, and that build stops, leaving `PIN` where it was, until:

- every patch here applies to it, and any patch it already carries is deleted;
- `Sources/TranscribeCpp` is re-vendored from it when the ABI hash moved, or
  when its `MAJOR.MINOR.PATCH` differs from the wrapper's `compiledVersion` -
  the wrapper refuses at load time to run against any other version, so the
  script refuses to build one.

Once it builds, the script writes the new release into `PIN`; review and commit
that with the patch changes, and re-run the measurements in `docs/` that name a
transcribe.cpp version. `./build.sh --no-update` (or the script run without
`--update`) builds the pin instead and prints a banner naming the newer release,
when the script finishes and again at the end of `./build.sh`.
