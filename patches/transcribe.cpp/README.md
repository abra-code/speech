# transcribe.cpp patches

`speech` does not link a published transcribe.cpp release. It builds one from
source: `tools/vendor-transcribe.sh` clones the pinned tag, applies every patch
in this directory, and builds `vendor/TranscribeCpp.xcframework`, which
`Package.swift` points at. The patches live here, in this repository, so the
same clone plus the same patches produce the same library on any machine.

Pinned tag and commit: `tools/vendor-transcribe.sh` (`PINNED_TAG`,
`PINNED_COMMIT`). Today that is `v0.2.3` at `63a44d9`.

## Layout

Patches directly in this directory apply at the root of the transcribe.cpp
clone. Patches in `ggml/` apply inside its vendored `ggml/` tree, because they
are written against the ggml repository and are meant to go to ggml unchanged -
transcribe.cpp keeps its own downstream ggml patches in `patches/ggml/` the same
way, which is why the numbering here starts at 0002: `0001` in that series is
upstream's threadpool patch, already in the tree we clone.

The vendored `ggml/` directory is generated by upstream's `scripts/sync-ggml.sh`
from an upstream ggml SHA plus that patch list. We patch the generated files
directly instead of re-running the sync script: the result is identical, and it
keeps the build off the network and off a second repository. The vendored ggml
SHA is `8c63e70982c95ceb862e3a1073a2c1beef75d60a`, identical at `v0.2.3` and on
`main`, so these two patches are not tied to the transcribe.cpp pin.

## The patches

### 0001-stream-commit-collapsed-spaces.patch

`src/transcribe.cpp`, plus a regression test in
`tests/stream_dispatch_unit.cpp`.

For the Parakeet cache-aware family the library's committed text stops growing 5
to 25 seconds into continuous speech (18 of 20 measured passages) and everything
after that is committed only at finalize. The commit boundary compares per-token
texts, each decoded on its own, against a full text whose runs of spaces have
been collapsed, so the first token that decodes to a bare space ends the match
for the rest of the stream. Partials stay current; finals, which refinement and
saved transcripts are built from, do not.

Measured on `ggml.nemotron-3.5-asr-streaming-0.6b` q8_0 over 20 continuous
LibriSpeech passages: finals 34.39 s behind the audio at the median and 54.27 s
at worst, on both an M5 and an M1 Pro. With this patch and no other change:
0.46 s median, 1.74 s worst, WER unchanged at 3.60%.

`SpeechGGML` also carries a Swift-side workaround for this defect
(`GGMLLiveSession.commitsTentative(for:)`, documented in `docs/live.md`). It is
inert against a patched library - it reads committed plus tentative as
committed, which is what the fixed library commits anyway - and stays until the
pin moves to a release that carries the fix.

Facts for the upstream issue and PR: `Private/transcribe-cpp-commit-freeze-facts.md`.

### ggml/0002-metal-null-check-buffer-alloc.patch

`ggml/src/ggml-metal/ggml-metal.cpp`. `ggml_backend_metal_buffer_type_alloc_buffer`
does not check `ggml_metal_buffer_init` for NULL and passes the result to
`ggml_metal_buffer_is_shared`, so a Metal allocation failure is a SIGSEGV
(`EXC_BAD_ACCESS` at `0x10`) rather than an error.

This is upstream ggml commit `e9c3b152bf`, "metal : null-check buffer alloc to
fix OOM crash (llama/25371)", dated 2026-08-25 - after the vendored SHA. It
leaves when the vendored ggml is bumped past that commit.

### ggml/0003-sched-check-reserve-result.patch

`ggml/src/ggml-backend.cpp`. `ggml_backend_sched_alloc_splits` ignores the result
of `ggml_gallocr_reserve_n` and calls `ggml_gallocr_alloc_graph` anyway, which
places tensors in a buffer that was never allocated: with 0002 alone the process
still dies, at `KERN_INVALID_ADDRESS` in `ggml_gallocr_alloc_graph`.

Not fixed upstream (ggml master still had the unchecked call on 2026-09-17), so
this one does not go away with a ggml bump. It belongs upstream in both ggml and
llama.cpp.

Together, 0002 and 0003 turn a crash into `run: out of memory` on the path
transcribe.cpp already handles: a 20-minute recording through Qwen3-ASR 1.7B
Q8_0, which asks Metal for 14.8 GB on a 24 GB machine, now exits 1 with every
step named in the log. Facts: `Private/transcribe-cpp-metal-oom-facts.md`.

## When a patch stops applying

The build fails, on purpose, and nothing is produced. A patch that no longer
applies means upstream changed the code a fix depends on, and the right response
is to look at what changed - not to ship a binary quietly missing the fix.

To rework one:

1. Clone the pinned tag by hand, or use the one the failed run left in
   `vendor/transcribe.cpp`. Read `vendor/transcribe.cpp/.speech-patch-state`
   first: a tree left by a failure carries the patches ordered *before* the
   failing one and none after it, so it is a diagnostic tree, not the patched
   source. Never build from it - it compiles perfectly well and produces a
   library missing fixes. Only a tree whose state file says `complete` is what
   the shipped framework was built from.
2. Apply what still applies, fix the rest against the new code, and re-measure
   what the patch claims above. The numbers in this file are the acceptance
   criteria.
3. Regenerate the patch with `git diff` from the clone root (`git diff` inside
   `ggml/` for the ggml series) and drop it back here under the same name.
4. Run `tools/vendor-transcribe.sh --force`.

If a fix has landed upstream, delete the patch instead and move the pin.

## When upstream publishes a release

Every build checks for a newer tag and prints a banner when
`tools/vendor-transcribe.sh` finishes, and `./build.sh` prints it again at the
end of its own output, after the Swift build log, from what that check recorded
in `vendor/.newer-tag`. It never fails the build, it costs one `git ls-remote`,
and it is skipped with `SPEECH_VENDOR_OFFLINE=1`. Moving
the pin means bumping `PINNED_TAG` and `PINNED_COMMIT`, re-vendoring
`Sources/TranscribeCpp` if the ABI hash moved (the script refuses to build on a
mismatch), dropping any patch the release now carries, and re-running the
measurements in `docs/` that name a transcribe.cpp version.
